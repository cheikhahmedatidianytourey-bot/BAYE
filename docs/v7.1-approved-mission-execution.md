# BAYE v7.1 — Approbation et exécution contrôlée

## Objectif

L'exécution d'une mission authentifiée exige désormais une autorisation explicite, signée, limitée à un graphe exact et utilisable une seule fois. L'approbation ne donne pas accès aux outils externes : le périmètre actuel reste l'inférence textuelle des spécialistes BAYE.

## Flux API

Toutes les routes ci-dessous exigent un jeton d'identité BAYE valide dans `Authorization: Bearer <identity-token>`.

### 1. Demander une approbation explicite

`POST /api/orchestration/{missionId}/approve`

Corps :

```json
{
  "approved": true,
  "tasks": [
    { "id": "research", "role": "research", "objective": "Analyser le besoin." },
    { "id": "quality", "role": "quality", "objective": "Examiner le résultat.", "dependsOn": ["research"] }
  ]
}
```

Le serveur valide le graphe et retourne un jeton d'approbation valable cinq minutes. L'appel d'approbation n'exécute aucune tâche.

### 2. Exécuter le même graphe

`POST /api/orchestration/run`

Corps : transmettre le même `missionId`, le même tableau `tasks` et le `approvalToken` reçu. Toute modification d'identité, de mission, d'objectif, de rôle, de dépendance, de budget ou d'ordre des tâches invalide l'approbation.

L'autorisation est consommée atomiquement dans PostgreSQL avant le lancement des spécialistes. Un rejeu, une panne du stockage anti-rejeu ou une approbation expirée bloque l'exécution. Si l'exécution échoue après consommation, il faut demander une nouvelle approbation.

## Périmètre de sécurité

- Signature HMAC-SHA256 avec comparaison en temps constant.
- Jeton lié à l'identité propriétaire, à l'identifiant de mission, à l'empreinte SHA-256 du graphe et à la liste ordonnée des tâches.
- Portée unique : `specialist:text_inference`.
- Durée maximale : dix minutes; l'API fixe actuellement cinq minutes.
- Nonce à usage unique, consommé avec une insertion PostgreSQL atomique.
- Le compte PostgreSQL applicatif reçoit uniquement USAGE sur le schéma et INSERT sur la table de nonces.
- Aucune permission d'exécuter des outils externes, de publier, d'effectuer un paiement ou de contacter un service tiers n'est accordée par cette approbation.

## Configuration requise

Configurer côté serveur :

- `BAYE_EXECUTION_APPROVAL_SECRET` : secret aléatoire d'au moins 32 octets. Exemple de génération : `openssl rand -hex 32`.
- `BAYE_EXECUTION_APPROVAL_DATABASE_URL` : URL PostgreSQL d'un compte applicatif dédié `baye_execution_approver`.

Préparer la base avec un compte administrateur :

1. Appliquer `migrations/0063_lifecycle_nonce_store.sql` dans le schéma `public`.
2. Créer séparément le rôle de connexion `baye_execution_approver` avec `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT` et un mot de passe géré par l'hébergeur de secrets.
3. Appliquer `migrations/0071_execution_approval_nonce_privileges.sql` dans le schéma `public`.
4. Configurer la variable de connexion avec ce compte. Le pool BAYE fixe `search_path=public`.

La migration ne crée aucun rôle, mot de passe, secret ou base de données. Ne pas utiliser le compte administrateur PostgreSQL comme compte applicatif. Ne pas réutiliser une base appartenant à un autre projet.

Si le secret ou la base n'est pas configuré, les routes d'approbation et d'exécution échouent de manière fermée. Les anciens appels anonymes à `/api/orchestration/run` ne sont plus acceptés : l'identité et l'approbation sont obligatoires.

## Validation

Les tests unitaires couvrent la signature, l'expiration, l'identité, l'empreinte du graphe, les tâches, le rejeu et les erreurs de stockage. Un test PostgreSQL conditionnel vérifie le rôle à privilèges minimaux et la consommation unique réelle sur une base locale jetable via `BAYE_TEST_DATABASE_URL`.

Cette version ne provisionne pas la base de production, les secrets, les rôles Render ou le déploiement. Le contrôle d'approbation protège uniquement l'exécution actuelle des spécialistes en inférence textuelle; l'exécution d'actions externes devra recevoir des portées et des politiques distinctes.
